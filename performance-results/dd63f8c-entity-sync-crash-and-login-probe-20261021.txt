Entity persistence, owner crash, and removal
--------------------------------------------
Backend A first force-loaded a disposable chunk; Backend B then subscribed. Backend A spawned one tagged persistent pig. Both RCON consoles observed UUID `[I; -586712015, -1695463928, -2132239864, 1359236121]` at `(18128.5,102,18000.5)`. Both backends acknowledged `save-all flush`; Backend A was force-killed while Backend B stayed up. Backend B still observed that UUID and position. After Backend A restarted from the same directory, both backends again returned the same UUID and position. A per-backend scoreboard count returned exactly one tagged pig on each backend. Backend B then killed it as the non-owner; both RCON consoles returned `No entity was found`. Across this crash/restart/removal run there were zero duplicate-UUID warnings and zero missing-entity request warnings. All processes exited and all six fixture ports closed.

The initially attempted unlimited `data get entity @e[tag=...]` query returned Minecraft's selector-cardinality error, which means the selector syntax permits multiple matches; it was not evidence of duplicate entities. The scoreboard count and UUID queries established one entity per backend.

Automated player login/movement probe and remaining anomaly
----------------------------------------------------------
Eight protocol-777 clients reached ready state through the built-in proxy and remained connected for the 61-second scripted run: 8/8 ready, 0 protocol disconnects, 0 unexpected socket ends, 0 client errors, 8,617 sent movement packets. RCON samples during the run saw player positions advance on both backends. This particular run did not capture authoritative positions across the ownership boundary, so it is not a boundary-movement or player-capacity pass. Its initial world was a disposable fixture with a prefilled route; a prior attempt against the same disposable fixture used the template's five-player cap and was discarded before this successful run after increasing the cap to 20.

The successful login window still emitted nine `RequestEntityPacket` warnings (`... requested entity <UUID>, but that entity doesn't exist`): eight during player login/chunk attachment and one during the early movement interval. They did not identify players. No duplicate-UUID, player-request, or “not in subscribed chunk” warnings appeared. All nine UUIDs were queried after the run on both backends and were absent from the currently loaded entity lookups. An NBT-aware scan of every Master entity region file in the fixture\'s Overworld, Nether, and End also found none of them. This makes a saved unloaded entity less likely, but does not prove where the updates originated or rule out a transient race before removal markers arrived. The root cause remains unresolved. Logs, event trace, and fixture data are under `%TEMP%\MultiPaper-dd63f8c-player-entity-20261021`.

Stable-release blockers
-----------------------
- Classify and resolve or deterministically rule out the repeated missing-entity requests from player login/movement. Earlier two-PC synthetic runs also reported a rejected duplicate Bat UUID insertion; the exact `dd63f8c` local run did not reproduce it.
- Repeat authoritative player movement across the ownership boundary on the two target PCs with the exact final JAR pair, then run representative workload/capacity tests. The current local scripted movement and older two-PC measurements are not sufficient to certify a safe maximum.
- Player-driven inventory/container actions during entity/chunk handoff, Mojang GUI/online-mode use, and remaining Survival/farm/portal/stasis coverage are not established by this RCON-only entity run.
