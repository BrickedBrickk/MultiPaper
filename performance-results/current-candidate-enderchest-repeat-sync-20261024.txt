Reproduction and root cause
---------------------------
With the five required Bukkit plugins enabled on both backends, a Mineflayer
operator opened another backend's Ender Chest through InvSee++. The sequence
deposited six emeralds, withdrew them remotely, redeposited them, then withdrew
them a second time. Before the fix, the second withdrawal left six emeralds in
the operator inventory while six remained in both Ender Chest views. Repeated
runs also exposed the stale-state condition on the first withdrawal.

Diagnostic slot tracing showed unchanged stacks were being emitted on every
tick and echoed between backends. `MultiPaperEnderChestHandler` compared a
snapshot copy using `ItemStack.equals`; ItemStack has no value-based `equals`
override, so distinct copies never compared equal. Replaced the comparison with
Minecraft's value-aware `ItemStack.matches`, which checks count and components.
Temporary diagnostic logging was removed. The regression runner now includes
the last authoritative backend state in failure output.

Exact-candidate verification
----------------------------
On the exact Paperclip hash above, with Floodgate, GrimAC, InvSee++, ViaBackwards,
and ViaVersion enabled on both backends, the runner asserted these states on
both servers after each operation:

1. Target deposit: owner chest 6, remote mirror 6, operator inventory 0.
2. Remote withdrawal: owner chest 0, remote mirror 0, operator inventory 6.
3. Remote redeposit: owner chest 6, remote mirror 6, operator inventory 0.
4. Second remote withdrawal: owner chest 0, remote mirror 0, operator inventory 6.

Every state conserved exactly six emeralds. Runner output ended with `PASS`.
`node --check scripts/Verify-InvSeeEnderChestCrossBackend.js` passed. All
disposable backend, Master, and ViaProxy listeners were stopped afterward.
This was an offline synthetic Java client test; it does not certify online-mode
login, Bedrock/Floodgate identity, or legitimate-client GrimAC behavior.
