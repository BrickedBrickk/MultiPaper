## Newly documented Master I/O ordering defect

Working-tree `MultiPaper-Master/.../RegionFile.java::submitTask` previously applied `orTimeout(15 seconds)` to the *previous task future*. `CompletableFuture.orTimeout` completes that future exceptionally but does not stop the underlying file I/O. Consequently a successor chained to the timed-out future could begin while the earlier disk operation was still active, violating per-region serialization and creating a real stale/out-of-order write risk. This is not evidence that the Crafty1 warnings caused the player reports.

The working-tree fix serializes task enqueueing, advances the chain only after the previous operation actually completes (while allowing a failed operation not to poison later work), and makes the delay warning-only. New latch regression `slowTaskWarningMustNotReleaseLaterRegionFileOperations` fails against the old timeout behavior and passes with the fix (retained red/green details below). ## Follow-up: close-versus-submit race

An independent source review found `RegionFile.close()` checked `lastTaskInQueue.isDone()` outside the monitor, then acquired the monitor only to close the file. A racing `submitTask` could append after the close-side queue check, so close could finish and the accepted task could run against the closed file. New deterministic test `closePreventsNewRegionFileTasksFromStartingAfterTheFileIsClosed` reproduced the old behavior: after close completed, task submissions were still accepted; red log SHA-256 `B5C85AE30BB1A0D8EC70F7180699D0F02398BFC2232D94583D30C22877DE341A`.

The fix has `close()` mark the region closing while synchronized, capture and drain the accepted queue, then close exactly once. Synchronized `submitTask` rejects work after closing begins with a failed future, so callers cannot mistake a post-close write for success.
